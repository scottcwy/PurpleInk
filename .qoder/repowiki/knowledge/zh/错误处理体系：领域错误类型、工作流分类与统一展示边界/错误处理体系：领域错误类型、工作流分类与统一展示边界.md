## 1. 系统与模式概述

该仓库采用「领域错误类型 + 工作流错误分类 + 统一展示边界」的分层策略，覆盖 Next.js 前端、独立渲染 Worker（server/）以及 AI/音频/编排管线。
- 前端通过 Next.js 的 `global-error.tsx` 与 `not-found.tsx` 提供根级错误边界与 404 页面，不暴露原始堆栈，仅显示类别与 digest。
- 各业务域（auth、ai、canvas、director）定义专用 Error 子类或结构化失败对象，用于在跨模块传播时保留语义。
- 工作流错误通过 `classifyWorkflowError` 按「类型优先 → 文案规则 → 阶段兜底」三段式归类为统一的 `WorkflowErrorCode`，并标注是否可重试。
- server 侧使用轻量 `errorMessage` 工具剥离 stack 后写入任务状态，避免泄露敏感信息。

## 3. 架构与约定
- 领域错误类型化
  - `UnauthenticatedError`、`ProviderUnavailableError`、`ArtifactValidationError` 等均为继承 `Error` 的类，设置固定 `name`，便于上层按类型识别而非依赖 message 文本。
  - 认证失败以 `AuthFailure` 结构体（`ok: false` + `code` + 可选 `detail`/`retryAfterMs`）表达，配合 `AUTH_FAILURE_STATUS` 与 `AUTH_FAILURE_MESSAGE` 把 code 映射到 HTTP 状态码与用户文案，避免泄露账号是否存在。
- 工作流错误分类
  - `classifyWorkflowError` 对任意 error 输出 `WorkflowErrorProjection`（code、stage、message、retryable、sourceNodeId），判定顺序严格为：
    1) `classifyByType`：zod 合同、`ArtifactValidationError`、`RouteContractError`、`RetryBudgetExhaustedError`、`ProviderUnavailableError` 等结构性错误；
    2) `classifyByMessage`：基于有序正则规则匹配外部原因（凭据、额度、缺失产物、队列、provider 超时等）；
    3) `classifyByStage`：按阶段名回落到 `QUEUE_FAILED` / `FABRICATE_FAILED` / `RENDER_FAILED` / `MEDIA_FAILED` / `STAGE_FAILED`。
  - 分类结果中的 `retryable` 决定 UI 是否展示重试按钮以及自动恢复策略是否重排。
- 前后端统一展示边界
  - Next.js 根错误边界 `global-error.tsx` 只展示类别与 digest，不提供原始错误内容；`not-found.tsx` 将「不存在」与「无权访问」统一为同一文案，避免泄露其他 workspace 对象存在性。
  - server 侧 `runJob` 捕获异常后仅写入 `error: errorMessage(err)`（即 `err.message` 或 `String(err)`），完整堆栈仅进入 `logger.error`，对外不泄露本机路径。

## 4. 约定与约束
- 认证失败不泄露账号状态：登录失败与验证码请求一律返回相同文案与状态码，真实发送与否由服务端决定（见 `src/features/auth/errors.ts` 注释与常量）。
- 工作流错误分类必须遵循「类型优先于文案」的顺序，新增错误来源需先判断是否为内部矛盾（应 `retryable=false`），再考虑文案规则（见 `docs/conventions/workflow-failure-patterns.md` 模式 B）。
- 兜底类别按阶段职责分配，禁止所有未识别错误都自称渲染失败（见 `workflow-error.ts` 中 `STAGE_FALLBACKS` 与模式 B 文档）。
- 异步媒体未就绪必须明确标记为 `MEDIA_NOT_READY`（`retryable=true`），且其文案含「缺少」，必须在 MESSAGE_RULES 中排在「上游产物缺失」之前（见模式 D）。
- 进程中断、重试预算耗尽、人为跳过、Provider 熔断四层容灾互斥，不得用同一错误码或状态混叙（见模式 H）。
- 测试与 fixture 必须使用真实产物形状，最小对象仅用于反向断言（见模式 E）。
- dev server 长驻进程可能持有旧模块，改动 queue handler/stage runner/model routing 后必须重启验证（见模式 F）。
- 可追加文件不得提前登记 artifact，哈希必须在生产者关闭后计算（见模式 G）。

## 5. 典型错误流转示例
- 认证失败：API 返回 401 → 客户端调用 `throwIfUnauthenticated` 抛出 `UnauthenticatedError` → 统一拦截打开登录弹窗，不各自 alert。
- AI 服务不可用：下游抛出 `ProviderUnavailableError` → `classifyByType` 直接映射为 `PROVIDER_FAILED`（`retryable=true`）→ UI 提示「AI 服务暂时不可用，可稍后重试或选择跳过」。
- Zod 合同错误：阶段输入校验失败 → `classifyByType` 映射为 `STAGE_INPUT_INVALID`（`retryable=false`）→ 文案列出具体字段路径，不泄露取值。
- 作业执行失败：`job-runner` catch 分支写入 `status: 'failed'` 与脱敏 `error` 字段，完整堆栈仅入日志。

## 6. 适用边界
- 该体系主要覆盖 Next.js App Router 前端、独立 purpleink-server 渲染 Worker，以及 AI/音频/编排管线中的结构化错误分类与展示。
- 脚本与迁移工具（scripts/migration/*）目前多使用裸 `throw new Error(...)` 并在入口 `.catch(() => {})` 收尾，不属于核心运行时错误体系。
