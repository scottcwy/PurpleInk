## 1. 系统/方法概述
本仓库采用「领域错误类型 + 工作流错误投影 + 统一用户文案」的分层策略，将原始异常（zod 校验失败、外部服务报错、进程中断等）归一为可重试性判定、可展示的业务错误码，并在前端通过 Next.js 错误边界与 API 响应结构呈现给用户。

- 领域层：各 feature 定义自己的错误类型与失败码（如 auth、ai、director、canvas），错误对象携带 `name` 字段以便上层按类型识别。
- 工作流层：`classifyWorkflowError` 把任意异常投影为 `WorkflowErrorProjection`（code/message/retryable/stage/sourceNodeId），判定顺序严格为「类型优先 → 文案规则 → 阶段兜底」。
- 表现层：Next.js `global-error.tsx` 作为根级错误边界，只展示类别与 digest；API 层通过 `authFailure` 结构与状态码映射返回用户可见文案。

## 2. 关键文件与包
- `src/features/auth/errors.ts` — 认证域失败码、HTTP 状态映射、`AuthFailure` 结构与构造器
- `src/features/canvas/workflow-error.ts` — 工作流错误分类器、13 种 `WorkflowErrorCode`、消息规则与阶段兜底
- `src/features/ai/provider-unavailable-error.ts` — Provider 熔断不可用错误（`ProviderUnavailableError`）
- `src/features/ai/route-contract-error.ts` — 路由/能力合同矛盾错误（`RouteContractError`）
- `src/features/director/artifact-validation-error.ts` — 产物校验失败错误（`ArtifactValidationError`）
- `server/src/lib/error-message.ts` — 对外仅暴露 `message` 的脱敏工具
- `src/app/global-error.tsx` — Next.js 根级错误边界，显示 digest 与重试入口
- `docs/conventions/workflow-failure-patterns.md` — 工作流失败模式手册（A~H 模式与护栏清单）

## 3. 架构与约定
- **错误类型命名约定**：自定义错误类必须覆盖 `name` 属性（如 `ProviderUnavailableError`、`RouteContractError`、`ArtifactValidationError`），以便 `classifyByType` 在文案匹配前精准归类。
- **分类优先级**：`classifyWorkflowError` 严格按 `classifyByType` → `classifyByMessage` → `classifyByStage` 执行，确保 zod 报文中的关键词不会误入外部服务规则。
- **可重试性语义**：每个 `WorkflowErrorCode` 明确标注 `retryable: boolean`。内部矛盾（合同不匹配、配置缺失）一律 `false`；外部抖动（网络超时、provider 不可用）为 `true`。
- **文案脱敏**：所有面向用户的 message 不得包含 provider 原始响应、prompt、凭据或模型名；zod 违规仅暴露字段路径，不暴露取值。
- **HTTP 状态映射**：认证失败通过 `AUTH_FAILURE_STATUS` 映射到 401/422/429/503，避免泄露账号是否存在。
- **四层容灾护栏**（文档模式 H）：租约回收（TASK_INTERRUPTED）→ 重试预算闸门（RETRY_BUDGET_EXHAUSTED）→ 人为跳过（skipped）→ Provider 熔断与备选降级（PROVIDER_FAILED）。

## 4. 约定与约束
- 新增错误来源必须先问「外部原因还是应用内部矛盾」，内部矛盾必须 `retryable=false`，禁止让 UI 展示无意义重试按钮。
- 兜底类别必须按阶段职责分配：`RENDER_FAILED` 仅限 RENDER 阶段，文本阶段使用 `STAGE_FAILED` 并带阶段名。
- 跨阶段数据结构只能有一个 zod 定义（模式 A），任何 prompt 输入 schema 不得内联重写上游契约。
- 异步媒体读取必须给出明确的 `MEDIA_NOT_READY`（`retryable=true`），且其文案含「缺少」，必须在消息规则中排在「上游产物缺失」之前。
- 测试 fixture 必须使用真实产物形状（模式 E），最小对象仅用于反向断言。
- 改动 queue handler、stage runner、模型路由后需重启 dev server 验证（模式 F），以节点状态变化而非代码外观为证据。
- artifact 登记必须在生产者关闭后计算哈希（模式 G），禁止提前登记可变文件。
- 所有对外错误信息仅保留 `message`，stack 与绝对路径走 logger 记录（`error-message.ts`）。

该体系通过类型化错误、集中分类与统一文案，使同一类失败不再重复发生，并为 UI 提供一致的可操作反馈（重试/跳过/修复配置）。
