## 1. 系统/方法概述
该仓库采用「领域专用 Error 类 + 统一分类器 + Next.js 错误边界」的分层策略：
- 业务层通过继承 `Error` 的领域错误类表达可区分故障（如配额耗尽、未认证、Provider 请求失败等）。
- 出网边界对第三方 AI Provider 的错误进行安全脱敏，封装为统一的 `ProviderRequestError`，并附带可重试时间、HTTP 状态码映射的 failure kind。
- Next.js 提供根级 `global-error.tsx` 与 `not-found.tsx` 作为 UI 侧兜底；服务端通过 `errorMessage` 仅暴露 message，不泄露堆栈或绝对路径。
- 工作流层使用错误分类逻辑（由 `classifyWorkflowError` 等模块驱动）基于错误类型与文案判定是否可重试、是否需要降级或熔断。

## 2. 关键文件与包
- 通用错误工具
  - `server/src/lib/error-message.ts`：对外只返回 `err.message`，屏蔽 stack/路径。
  - `server/src/lib/logger.ts`：轻量 console 日志，error/warn/info 三档。
- 领域错误类型（按功能域组织在 `src/features/*`）
  - `src/features/auth/unauthenticated-error.ts`：`UnauthenticatedError` + `throwIfUnauthenticated` 拦截 401。
  - `src/features/billing/contracts.ts`：`QuotaExhaustedError`（code=`quota_exhausted`）、`BillingIdempotencyConflictError`（code=`idempotency_conflict`）。
  - `src/features/ai/provider-request-error.ts`：`ProviderRequestError`，含 `ProviderFailureKind` 枚举、`providerFailureKind(status)`、`providerErrorFromResponse`、`providerNetworkError`、`parseRetryAfter`。
  - `src/features/ai/provider-unavailable-error.ts`：`ProviderUnavailableError`，固定文案用于“主备均不可用”场景。
  - `src/features/ai/route-contract-error.ts`：`RouteContractError`，表示路由/能力合同矛盾，避免被误判为外部抖动。
  - `src/features/director/artifact-validation-error.ts`：`ArtifactValidationError`。
  - `src/features/director/director-billing-stream.ts`：`DirectorPreflightError`，标记出网前审计/计费上下文缺失。
  - `src/app/(auth)/_components/auth-api.ts`：`AuthRequestError`。
  - `src/app/products/(app)/canvas/[projectId]/canvas-action-api.ts`：`BillingQuotaExhaustedError`。
  - `src/features/projects/project-compatibility.ts`：`UnsupportedProjectWorkflowError`。
  - `scripts/migration/sqlite-backup.ts`：`CliInputError`（CLI 脚本专用）。
- Next.js 错误边界与页面
  - `src/app/global-error.tsx`：根级错误边界，显示 digest 参考号，提供“返回首页/重试”。
  - `src/app/not-found.tsx`：根级 404，统一“不存在/无权访问”文案，避免信息泄露。

## 3. 架构与约定
- 错误分类优先于文案匹配
  - 文档注释多次强调：带类型的错误让分类器在文案匹配之前就按类型判定（例如 `RouteContractError`、`ProviderUnavailableError`），避免把配置错误或外部抖动误判为可重试。
- Provider 出网边界的错误安全化
  - `ProviderRequestError` 的 `message` 由 `safeProviderMessage` 生成，不包含响应正文、Prompt、凭据或工具参数；原始异常仅保存在内存中的 `cause`，禁止序列化进节点/Artifact/task_attempts.failure。
  - HTTP 状态码到 `ProviderFailureKind` 的映射集中在 `providerFailureKind`，支持 auth/balance/permission/rate_limit/request/safety/timeout/unavailable/network/unknown。
  - `retry-after` 头解析为 `retryAt`，配合调度层的 defer 实现退避。
- 客户端 401 统一处理
  - `UnauthenticatedError` 配合 `throwIfUnauthenticated` 在各客户端 API 模块中集中捕获，交由 `useRequireLogin().handleAuthError` 打开登录弹窗，避免各自 alert/跳转。
- 计费/配额错误具象化
  - `QuotaExhaustedError` 携带 `code` 与 `billingUrl`，便于上层直接跳转到 `/products/billing`。
- 渲染 Worker 与服务端日志
  - `logger.ts` 仅输出 `[INFO|ERROR|WARN] event data`，错误详情走结构化日志而非直接回显给调用方。
- Next.js 错误边界规范
  - `global-error.tsx` 自带 `html/body`，不依赖 Providers/字体/主题脚本，仅展示类别与 digest，不回显原始错误内容。
  - `not-found.tsx` 刻意不区分“不存在”与“无权访问”，遵循 `docs/conventions/routing.md §9.2` 的安全约定。

## 4. 约定与约束
- 所有跨进程/跨模块传播的业务错误必须使用自定义 `Error` 子类，禁止直接抛裸 `Error` 进入工作流层。
- 涉及外部 Provider 的请求失败必须通过 `ProviderRequestError` 或其工厂函数包装，不得透传原始网络/SDK 异常。
- 错误消息不得包含敏感信息（凭据、Prompt、模型名、工具参数），仅保留人类可读的类别指引。
- 401 响应必须在客户端 API 层立即转换为 `UnauthenticatedError`，由统一入口处理登录态恢复。
- 配额耗尽与幂等冲突等计费错误需携带稳定 `code`，以便前端路由到计费页或提示幂等冲突。
- 根级错误边界与 404 页面不暴露内部细节，仅展示 digest/参考号与操作按钮。
- 脚本/CLI 错误可使用简单 `Error`，但应在顶层 `.catch` 中打印 `error instanceof Error ? error.message : String(error)`，避免堆栈泄露。

## 5. 典型流程示例
- AI 调用失败：`fetch`/SDK 抛出 → `providerErrorFromResponse` / `providerNetworkError` → `ProviderRequestError` → 工作流分类器根据 `kind` 决定重试/降级/熔断 → 若全部不可用则抛出 `ProviderUnavailableError`。
- 用户未登录：API 返回 401 → `throwIfUnauthenticated` → `UnauthenticatedError` → `useRequireLogin` 拦截并弹出登录框。
- 配额耗尽：计费检查失败 → 抛出 `QuotaExhaustedError`（code=`quota_exhausted`）→ 前端跳转 `/products/billing`。
- 路由能力不匹配：校验失败 → 抛出 `RouteContractError` → 分类器识别为“非外部抖动”，不触发重试。
