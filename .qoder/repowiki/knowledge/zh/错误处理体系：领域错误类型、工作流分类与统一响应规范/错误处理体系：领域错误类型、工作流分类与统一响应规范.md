## 1. 系统/方法概述
本仓库采用「领域专用 Error 类 + 集中式错误分类器 + 统一响应包装」的分层策略：
- 各业务域（auth、billing、ai、director、queue）定义语义明确的 `Error` 子类，通过 `name` 字段被上层分类器识别。
- 工作流错误由 `classifyWorkflowError` 统一归类为 `WorkflowErrorCode`，并输出 `retryable` 标志供队列重试决策使用。
- API 路由层不直接暴露原始堆栈，仅返回人类可读的 `message`；服务端日志保留完整细节。
- Next.js 根级 `global-error.tsx` 作为客户端全局兜底，只展示 digest 与操作按钮，不泄露异常详情。

## 3. 架构与约定
- **错误类型命名约定**：所有自定义错误均继承 `Error` 并覆盖 `name` 属性（如 `ProviderUnavailableError`、`RetryBudgetExhaustedError`、`QuotaExhaustedError`），以便上层按类型判定而非字符串匹配。
- **三段式分类优先级**：`classifyWorkflowError` 严格按「类型判定 → 文案正则匹配 → 阶段兜底」顺序执行，确保结构化错误优先于模糊文案判断。
- **安全原则**：认证端点不泄露账号是否存在（统一 401/200 文案）；工作流分类器不回显 provider 原始响应、prompt、凭据或隐藏推理路径。
- **重试语义**：每个分类结果包含 `retryable: boolean`，由队列层的 `shouldAutoRetry` 调用，结合 `MAX_AUTO_RETRIES=2` 与指数退避（5s 起步 ±20% 抖动）控制自动重试。
- **毒任务保护**：同一 fingerprint 在 30 分钟窗口内失败 ≥5 次即抛 `RetryBudgetExhaustedError`，拒绝再次入队。
- **响应包装**：服务端通过 `errorMessage(err)` 仅提取 `err.message`，避免泄露 stack 或绝对路径；客户端通过 `throwIfUnauthenticated` 将 401 转为 `UnauthenticatedError` 由统一拦截处理。

## 4. 约定与约束
- **认证错误必须使用 `AuthFailureCode` 枚举**，并通过 `AUTH_FAILURE_STATUS` / `AUTH_FAILURE_MESSAGE` 映射到 HTTP 状态码与用户文案，禁止在各路由自行拼接差异文案。
- **工作流错误必须经 `classifyWorkflowError` 归类**，禁止在队列层直接用 `includes` 自判是否重试。
- **外部服务错误必须抛出带 `name` 的 Error 子类**（如 `ProviderUnavailableError`、`RouteContractError`），使分类器能在文案匹配前准确识别。
- **客户端全局错误边界不得显示原始错误内容**，仅展示 digest 与「返回首页」「重试」按钮。
- **测试中验证的错误映射行为**（如导出路由对 409 的阻塞问题响应、401 的未认证错误转换）构成实际约束，新增分支需保持兼容。

## 5. 置信度评估
该体系在多个领域（认证、AI 路由、计费、队列、渲染）形成一致模式，且有专门的分类器与测试覆盖，属于高置信度的成熟实践。
