## 1. 使用的系统/工具链
- **包管理**: pnpm workspace（pnpm@10.30.0，通过 `packageManager` 字段与 `corepack` 锁定版本）
- **前端构建**: Next.js 16（`next build` / `next start`），未启用 `output: 'standalone'`，整份 `node_modules` 打入运行镜像
- **后端运行时**: Node.js + tsx 直接执行 TypeScript 源码（`tsx src/index.ts`），无预编译产物
- **测试**: Vitest（根 `vitest.config.ts`，Postgres 集成测试用 `vitest.pg.config.ts`）
- **数据库迁移**: Drizzle Kit（`drizzle-kit generate`）+ tsx 脚本（`scripts/setup/db-migrate.ts`）
- **容器化**: 多阶段 Docker 构建（根 `Dockerfile`、`server/Dockerfile`、`deploy/reverse-proxy/Dockerfile`）
- **编排**: docker-compose（`docker-compose.dev.yml` 开发环境，`docker-compose.prod.yml` 生产环境）
- **代码质量**: ESLint 9 + Prettier 3（`.prettierrc`、`eslint.config.mjs`）

## 2. 关键文件与位置
- 工作区定义: `pnpm-workspace.yaml`（包含 `.`、`server`、`packages/*`）
- 根包配置: `package.json`（统一 scripts、依赖、pnpm 配置）
- 服务端包: `server/package.json`（独立入口 `src/index.ts`，依赖 `@purpleink/procedural-sfx` via `workspace:*`）
- 程序化音效库: `packages/procedural-sfx/package.json`（纯 TS 模块，`exports` 指向 `./src/index.ts`）
- 容器镜像: `Dockerfile`（Next 应用）、`server/Dockerfile`（worker）、`deploy/reverse-proxy/Dockerfile`（Caddy）
- 编排文件: `docker-compose.dev.yml`、`docker-compose.prod.yml`
- 本地启动器: `scripts/dev/start-dev.ps1`（PowerShell 一键拉起 Postgres → 安装依赖 → 迁移 → 启动 web/worker）
- 验证脚本: `scripts/verify/` 目录下的架构基线、E2E 冒烟、Motion 基线等

## 3. 架构与约定
- **Monorepo 分层**:
  - 根 `package.json` 作为 Web 应用入口，通过 `pnpm --filter purpleink-server dev` 启动 worker
  - `server/` 是独立的 Node 服务，与 Next 共享 `pnpm-lock.yaml` 但各自维护 `node_modules` 与 `package.json`
  - `packages/procedural-sfx` 以 `workspace:*` 被根与 server 共同引用，实现跨包依赖解析
- **Docker 多阶段构建策略**:
  - `deps` 阶段：在 Linux 镜像内执行 `pnpm install --frozen-lockfile`，确保 ffmpeg-static/sharp 等平台二进制正确下载
  - `build` 阶段：`NODE_ENV=production` 下 `next build`，触发 `next.config.ts` 的 `removeConsole` 分支
  - `migrate` 阶段：保留 devDependencies（tsx/drizzle-kit），供一次性迁移任务使用
  - `runtime` 阶段：仅拷贝必要文件（`.next`、`public`、`assets/fonts`、`package.json`），非 root 用户 `pwuser` 运行
- **Playwright 浏览器安装分离**：构建期设置 `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`，运行期按 `node_modules/playwright/package.json` 中实际版本动态 `install chromium`，避免宿主与容器 Chromium 版本不一致
- **字体选择约束**：放弃 60MB 的 `fonts-noto-cjk`，改用 7.5MB 的 `fonts-wqy-zenhei`（文泉驿正黑），覆盖简繁中文且构建网络更稳定
- **反向代理网关**：Caddy 2.10-alpine 作为唯一对外暴露端口（443），内置 TLS、IP 白名单（`CVC_ALLOWED_CIDRS`）与 Basic Auth（secrets 挂载）
- **环境变量注入顺序**：生产环境通过 `docker-compose.prod.yml` 集中声明所有敏感变量（`POSTGRES_PASSWORD`、`CVC_CREDENTIAL_MASTER_KEY`、各 API Key），由 `bootstrap-credentials` 一次性任务校验并写入加密存储，运行时只读 DB

## 4. 约定与约束
- **Node/pnpm 版本锁定**：`engines.node >= 22.11.0`，`packageManager: pnpm@10.30.0`，启动脚本会校验版本并报错
- **依赖安装幂等性**：`start-dev.ps1` 比较 `pnpm-lock.yaml` 与 `node_modules/.modules.yaml` 时间戳决定是否重新 `pnpm install`，避免每次启动都重装
- **端口冲突处理**：默认自动寻找空闲端口（Web 3000、Worker 8787），支持 `-KillPort` 强制释放或 `-StrictPort` 严格失败
- **健康检查契约**：Next 提供 `/api/ping`，worker 提供 `/health`，反向代理通过 `depends_on` 与 `condition: service_healthy` 保证启动顺序
- **单实例约束**：Next 服务 `replicas: 1`，因 `stream-bus` / `status-bus` 基于进程内 `globalThis` 状态，多实例不安全
- **构建上下文要求**：server 与根 Dockerfile 必须以仓库根为构建上下文（`context: .`），否则无法解析 workspace 依赖
- **禁止提交密钥**：`.env.local`、`server/.env`、`deploy/reverse-proxy/secrets/basic_auth_credentials` 均 `.gitignore`，启动脚本仅检查键名不打印值
- **迁移前置**：`next` 服务 `depends_on` 要求 `migrate` 服务 `completed_successfully`，确保 schema 一致后再启动应用
- **tsx 执行方式**：CMD 直接调用 `node_modules/.bin/tsx`（POSIX shebang），而非 `node node_modules/.bin/tsx ...`，避免 shell 代码被当 JS 解析报错
