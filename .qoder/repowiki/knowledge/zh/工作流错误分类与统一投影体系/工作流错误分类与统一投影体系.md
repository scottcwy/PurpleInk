本仓库采用「类型优先 + 文案规则 + 阶段兜底」的三层错误分类机制，将任意阶段的异常统一投影为可展示、可判定是否重试的 `WorkflowErrorProjection`（schemaVersion=2），贯穿 Next.js API 路由与独立渲染 Worker。

## 1. 系统与方法
- **核心入口**：`src/features/canvas/workflow-error.ts` 中的 `classifyWorkflowError(error, { stage, sourceNodeId })`，所有业务层 catch 块最终都调用此函数。
- **三层判定顺序**：
  1. `classifyByType`：按 `error.name` 精确匹配结构化错误（ZodError、RouteContractError、ProviderUnavailableError、RetryBudgetExhaustedError 等），避免被文案规则误判。
  2. `classifyByMessage`：按有序正则规则匹配外部原因（凭据、额度、缺失产物、队列、provider 超时等）。
  3. `classifyByStage`：按阶段名给出默认类别（QUEUE/FABRICATE/RENDER/MEDIA_NARRATION → QUEUE_FAILED/FABRICATE_FAILED/RENDER_FAILED/MEDIA_FAILED）。
- **统一投影结构**：`WorkflowFault`（code、origin、stage、title、message、retryable、recovery、referenceId、occurredAt）由 `completeWorkflowFault` 补齐 stage/sourceNodeId/referenceId/occurredAt，并通过 Symbol 缓存到原始 Error 上避免重复计算。

## 2. 关键文件与包
- `src/features/canvas/workflow-error.ts` — 分类器主逻辑
- `src/features/canvas/workflow-fault.ts` — 错误码枚举、投影类型、Provider 错误投影、呈现映射
- `src/features/ai/provider-request-error.ts` — 出网边界唯一允许的 Provider 异常，含 httpStatus/kind/retryAt/requestId
- `src/features/ai/provider-unavailable-error.ts` — 主备均不可用时的专用错误
- `src/features/ai/route-contract-error.ts` — 路由/能力合同矛盾错误
- `server/src/server/internal-render-request.ts` — 内部渲染请求校验错误（InternalRenderRequestError）
- `server/src/lib/error-message.ts` — 对外只暴露 message，丢弃 stack
- `src/app/global-error.tsx` — Next.js 根级错误边界，仅显示 digest 参考号
- `tests/worker-error-hygiene.test.ts` — 断言 worker 不持久化/回显 stack

## 3. 架构与约定
- **错误传播边界**：Worker 侧通过 `errorMessage(err)` 剥离 stack，仅保留 message；HTTP 500 响应体不得直接内插 `String(err)`。
- **Provider 错误归一化**：所有第三方服务异常必须包装为 `ProviderRequestError`，由 `projectProviderFault` 映射为 PROVIDER_* 系列 code，区分 userFunded/platform 并给出不同 recovery 建议。
- **安全约束**：分类器注释明确禁止回显 provider 原始响应、prompt、凭据或隐藏推理；zod 违规路径仅暴露字段名，不暴露取值。
- **可重试性决策**：每个投影附带 `retryable: boolean`，由分类器根据错误性质决定（如 QUOTA_EXHAUSTED/CONFIGURATION_BLOCKED 不可重试，PROVIDER_FAILED/QUEUE_FAILED 可重试）。
- **跨模块解耦**：canvas 层仅通过 error.name 识别其他模块的错误类型，避免反向依赖 director/ai 等模块。

## 4. 约定与约束
- 所有业务层 catch 块必须调用 `classifyWorkflowError` 而非直接透传原始错误。
- 外部服务异常必须使用 `ProviderRequestError` / `ProviderUnavailableError` / `RouteContractError` 等具名错误类，禁止抛普通 Error 混入文案规则。
- 错误信息中不得包含敏感数据（凭据、prompt、stack、绝对路径），仅保留用户可读的 title/message 和 referenceId。
- 测试通过 `worker-error-hygiene.test.ts` 强制验证：job runner 使用 `errorMessage`、HTTP 500 不直接返回 `String(err)`。
- 错误投影 schemaVersion=2 作为版本标记，防止旧格式混淆。
