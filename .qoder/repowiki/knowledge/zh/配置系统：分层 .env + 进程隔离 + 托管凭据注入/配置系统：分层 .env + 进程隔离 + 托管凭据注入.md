## 1. 使用的系统与工具
- 无第三方 dotenv 库，后端使用自实现的极简 `loadEnv`（`server/src/lib/load-env.ts`）按行解析 `.env` 文件并注入 `process.env`。
- Next.js 通过内置 `@next/env` 的 `loadEnvConfig` 在脚本中加载根目录环境变量；`next.config.ts` 直接读取 `process.env` 中的变量控制构建与重写规则。
- 配置文件以 `.env.example` / `.env.local` 形式存在，真实值仅放在被 git 忽略的文件中，禁止提交 secret。

## 2. 核心文件与位置
- 根环境模板：`.env.example`（Next 进程消费变量说明与安全约束）
- Worker 环境模板：`server/.env.example`（采集/渲染 worker 专用）
- TTS 独立模板：`config/tts.env.example`
- 后端入口与环境加载：`server/src/index.ts`、`server/src/lib/load-env.ts`
- Next 配置：`next.config.ts`（`BACKEND_ORIGIN`、`CVC_NEXT_DIST_DIR`、`NEXT_PUBLIC_*`）
- AI 配置解析（StepFun/Gemini/MiMo 等）：`src/features/ai/config.ts` 及同目录下各 provider 的 `*-config.ts` 文件
- 安全契约测试：`tests/env.test.ts`（断言示例文件与实际消费变量对齐）

## 3. 架构与约定
### 3.1 进程级环境隔离
- **Next 进程** 与 **server/worker 进程** 各自维护独立的 `.env` 模板与运行时文件，互不交叉作为唯一真值。根 `.env.example` 明确声明“只列 Next 进程直接或经 bootstrap 间接消费的变量”，TTS 与 worker 相关变量放在 `server/.env.example` 与 `config/tts.env.example`。
- Worker 启动时按顺序加载两个文件：先 `server/.env`，再仓库根 `.env.local`（后者可覆盖同名键），实现本地开发时的覆盖机制。

### 3.2 环境变量加载策略
- `loadEnv(envPath)` 逐行解析，跳过空行与注释，去除首尾引号，且**已存在的 `process.env` 键不会被覆盖**（后加载文件优先覆盖）。
- Next 侧通过 `next.config.ts` 直接读取 `process.env` 中的 `BACKEND_ORIGIN`、`CVC_NEXT_DIST_DIR`、`NODE_ENV` 等变量，用于 rewrites、distDir、console 移除策略等。
- 部分脚本（如 `scripts/migration/*`、`scripts/setup/bootstrap-credentials.ts`）显式调用 `@next/env` 的 `loadEnvConfig(process.cwd())` 加载根环境变量。

### 3.3 配置来源优先级与类型划分
- **默认值（default）**：代码内硬编码的默认模型名、baseUrl 等（如 StepFun 的 `DEFAULTS` 表）。
- **环境变量（env）**：通过 `process.env[KEY]` 读取，支持覆盖默认值（如 `STEPFUN_BASE_URL`、`GEMINI_BASE_URL`、`MIMO_BASE_URL` 等）。
- **托管凭据（managed）**：平台托管的 API Key 通过 `resolveManagedCredential(provider)` 从数据库/服务目录动态获取，而非直接读 env，避免敏感信息泄露。
- **设置写入限制**：某些字段（如 StepFun baseUrl）不允许通过 UI 设置持久化，必须通过环境变量配置，否则抛出错误。

### 3.4 前端公开变量规范
- 仅允许 `NEXT_PUBLIC_*` 前缀的变量暴露到浏览器，且严格限制为非敏感配置（如 `NEXT_PUBLIC_API_BASE`、`NEXT_PUBLIC_SITE_URL`）。
- 认证、邮件通道等敏感变量（`CVC_MAIL_SMTP_*`）仅在 Next 服务端读取，不会下发到客户端。

## 4. 约定与约束
- **安全约束（AGENTS.md §7）**：所有 secret 类变量（API key、master key、口令）在 `.env.example` 中必须留空；真实值仅写在被 git 忽略的 `.env.local` 或 `server/.env` 中；禁止提交、禁止硬编码进源码。
- **禁止携带 secret 的 `NEXT_PUBLIC_*`**：任何可能泄露敏感信息的变量不得以前缀暴露给浏览器。
- **变量命名隔离**：Next 侧使用 `CVC_*` 前缀区分产品变量，worker 侧使用 `SMTP_*`、`IMAP_*`、`STEP_*` 等前缀，避免混淆。
- **TTS 配置独立**：TTS 相关变量不在根 `.env.example` 中出现，由 `server/.env.example` 与 `config/tts.env.example` 分别管理，测试强制验证这一分离。
- **向后兼容旧变量**：`GEMINI_API_KEY`、`STEPFUN_API_KEY` 等旧变量仅供历史/自定义凭据 bootstrap，不是内置托管服务的执行来源。
- **缺失即失败**：关键配置缺失时（如 SMTP 通道未配置），API 返回明确的 503 状态码，不会静默假装成功。

## 5. 验证与测试保障
- `tests/env.test.ts` 通过静态分析 `.env.example` 文件，断言敏感变量值为空、Next 侧与 worker 侧变量分离、以及未被 Next 消费的变量已从根模板移除。
- 各 provider 的 `*-config.test.ts` 文件验证配置解析逻辑的正确性。

## 6. 部署与编排集成
- Docker Compose 通过 `docker-compose.dev.yml` / `docker-compose.prod.yml` 注入环境变量。
- 反向代理（Caddy）的 Basic Auth 凭据通过 `deploy/reverse-proxy/secrets/` 目录管理，与业务配置分离。
- 种子脚本（`scripts/setup/seed-owner-account.ts`）支持 `--from-env` 模式从环境变量创建演示账号。
