# MiMo Provider、媒体容灾与设置页重构设计

## 背景与根因

PurpleInk 当前同时存在两类问题：

1. 供应商配置以表单字段为中心。Gemini、StepFun 与自定义 OpenAI-compatible
   的凭据、模型和路由分散在不同代码中，运行时并不知道供应商实际支持哪些能力。
2. `INGEST` 在提交文本产物前同步等待全部 TTS。任一音频请求失败时，文本快照、
   分镜拆解、代码生成也全部停止。这与文本和媒体应独立推进的工作流目标冲突。

StepFun 的近期真实探测还证明：模型列表可读并不代表推理额度可用。当前凭据可以列出
模型，却在 chat 与 TTS 上同时返回 HTTP 402，因此不能把“验证 Key”简化为列模型。

## 目标

- 将 Gemini、阶跃星辰、MiMo、自定义 OpenAI-compatible 作为四个明确的供应商身份。
- 用统一能力注册表约束文本、视觉、TTS、ASR 的可选供应商和默认模型。
- MiMo 默认使用：
  - 文本与视觉：`mimo-v2.5`
  - TTS：`mimo-v2.5-tts`
  - ASR：`mimo-v2.5-asr`
  - `mimo-v2.5-tts-voicedesign` 与 `mimo-v2.5-tts-voiceclone`
    作为高级可选模型，不作为默认路径。
- 文本主链路不再因 TTS/ASR 失败停止；媒体分支失败必须可见、可恢复、不得伪造时长。
- 设置页以用户任务组织信息，而不是暴露内部存储结构。

## 方案比较

### A. 扩展现有纵向表单

增加一组 MiMo 输入框和下拉框。实施最快，但供应商、能力和路由继续混在一起，
第四个供应商会显著放大认知负担，也无法从结构上避免把不支持 TTS 的供应商选入媒体路由。

### B. 能力注册表 + 供应商详情 + 路由矩阵（采用）

运行时和 UI 共用能力注册表。页面先展示四张供应商摘要卡，再在一个详情编辑区配置
连接和模型，最后用按能力过滤的路由矩阵决定节点实际使用谁。它可以在一次实现中消除
类型、API、运行时与 UI 的四套隐式判断。

### C. 初次配置向导

适合首次接入，但不适合频繁切换模型和排查工作流。向导可以以后作为注册表之上的入口，
本次不增加第二套状态模型。

## 供应商与能力模型

新增单一注册表，定义稳定 ID、显示名、能力、默认端点、默认模型和认证约束：

| Provider | text | vision | TTS | ASR |
| --- | --- | --- | --- | --- |
| `gemini` | 是 | 是 | 否 | 否 |
| `stepfun` | 是 | 是 | 是 | 是 |
| `mimo` | 是 | 是 | 是 | 是 |
| `openai-compatible` | 是 | 可声明 | 否 | 否 |

AI 路由只接受拥有对应 AI 能力的供应商；媒体路由只接受 StepFun 或 MiMo。
每次保存路由时服务端再次执行能力校验，不能只依赖前端禁用。

MiMo 使用 OpenAI Chat Completions 协议：

- 文本/视觉：`POST {baseUrl}/chat/completions`
- TTS：同一端点，待合成文本放在 `assistant` message，`audio.format=wav`，
  默认音色为 `mimo_default`
- ASR：同一端点，用 `input_audio` data URL，`asr_options.language=auto`

媒体调用使用非流式响应。TTS 解码 `message.audio.data` 的真实字节后继续沿用现有
ffmpeg 实测时长；ASR 读取 `message.content`。MiMo ASR 当前不提供 PurpleInk
现有 StepFun SSE 的逐词时间戳，因此它只能生成内容可追溯的分段字幕，不能伪称拥有
词级原生时间戳。

## 凭据与环境约束

凭据继续只存 `provider_credentials` 的加密字段。`.env.local` 仅允许保存非敏感的
端点和默认模型，不新增明文 Key fallback。

MiMo 的 `tp-` Token Plan 凭据只允许编程工具用途，官方当前禁止用于自定义应用后端的
非编码调用。设置 API 因此只接受用于产品 API 的 `sk-` 凭据；`tp-` 返回 422 且不覆盖
已有 secret。现有自定义供应商中的配置和密钥保持原样，不删除、不复制到 MiMo。

保存 MiMo Key 前执行最小 chat inference，而不是仅列模型；TTS/ASR 另有可选的能力探测，
状态分别展示，避免把“文本连接成功”误报为“音频可用”。

## 异步媒体分支

采用两阶段提交，不在 INGEST 中等待音频：

1. INGEST 校验模型输出后，立即提交只含 `scriptUnits` 的文本产物并创建镜头。
2. 同一工作流动作异步排入 narration 媒体任务。
3. DIRECT 与 SHOT_SPEC 可基于文本继续；依赖真实帧数的 FABRICATE 在音频分配尚未完成时
   进入明确的 `waiting-media`，而不是 `failed`。
4. narration 成功后提交独立且不可变的音频 manifest/allocation 产物，并唤醒等待节点。
5. narration 失败时记录媒体错误和 retryable 状态；文本节点保持已完成。
6. 用户点击“修复并继续”时只为媒体根节点新增一次尝试。若主媒体供应商出现
   provider/额度类错误且备用供应商已配置并通过对应能力探测，可有界尝试一次备用供应商；
   不循环重试。
7. 音频版本变化后，所有消费真实帧数的成功下游标记 stale 并重建。

文本分支允许在没有音频的情况下推进到 SHOT_SPEC；最终渲染仍必须拥有真实测量的音频，
除非项目明确选择“无旁白导出”。本次不引入估算时长或静音占位。

## 设置页信息架构

页面分为三层：

1. **供应商概览**：四张可选择的摘要卡，展示连接状态和 text/vision/TTS/ASR 能力标签。
2. **当前供应商详情**：连接信息、凭据状态、模型分组、独立能力检测。Key 始终只写不读。
3. **工作流路由**：按“规划与生成、视觉验收、媒体”分组的矩阵。供应商选项按能力过滤，
   同行展示有效模型与配置来源。

保存动作贴近当前区域；连接验证和路由保存分开反馈。所有错误只展示安全投影，
不展示原始响应、prompt、堆栈或凭据。

## 兼容性与非目标

- 不批量迁移或删除历史 Artifact；新媒体产物使用新版本和 lineage。
- 不删除现有 StepFun 路径；它仍可作为可配置的媒体供应商或有界备用。
- 不让自定义兼容服务默认宣称支持媒体。
- 不实现 MiMo voice clone 的样本上传流程；本次仅登记模型并在 UI 标为需要参考音频。
- 不新增队列系统；复用现有任务、节点状态和推进服务。

## 验收

- 四个供应商在 API、类型、运行时和 UI 中身份一致。
- 不支持某项能力的供应商无法保存到该路由。
- MiMo TTS/ASR 请求形状符合官方 Chat Completions 协议。
- `tp-` 凭据被服务端拒绝且不会覆盖旧 Key。
- TTS 失败后 INGEST 文本与镜头仍成功，DIRECT/SHOT_SPEC 可继续。
- FABRICATE 在等待真实音频时显示等待而非失败；媒体恢复后自动继续。
- 设置页在真实 Chromium 中可配置四个供应商和各能力路由，无新增控制台错误。
- 使用合法的 MiMo 产品 API 凭据时完成真实 text、TTS、ASR 探测；没有合法凭据时诚实报告
  未执行，不以 mock 冒充真实验证。
