# 02 · 视觉回归基线设施

- 前置：01 完成（基线必须含校准后的 150ms）
- 后续解锁：03 / 04 / 05 / 06（它们都需要基线来证明"只改了该改的"）
- 共用硬边界与验证清单见 `00-README.md` §0

## 1. 目标与非目标

**目标**：把本轮已经写好的一次性取证脚本升级为常驻的、带基线比对的验证设施，
让后续每个改动效的批次都能自动回答一个问题：**除了该变的，还有什么变了？**

**为什么这件事必须先做。** 本轮已经付过一次学费：规范文档里一处
`duration-[var(...)]` 被 Tailwind 扫成候选类，生成非法 CSS，
整份样式表解析失败、`/playbook/motion` 直接 500——而 `pnpm lint`、`typecheck`、
`test`、`verify:v3`、`build` **全部通过**（生产构建的 lightningcss 静默丢弃了非法声明）。
只有真实浏览器打开页面才暴露。动效改造的绝大多数缺陷都属于这一类：
类型正确、测试通过、构建成功，但页面不对。

**非目标**：不做全站 46+ 组件族的基线。只覆盖两个对照台页面 + 少量真实路由，见 §3.2。

## 2. 现状

已存在的素材：

- `.data/motion-playbook-shot.mjs`（本轮产出，未纳入版本控制）已实现：
  亮/暗双态访问两个 playbook 页、状态码检查、console 错误与警告收集、
  失败请求收集、计算样式断言（四档时长解析值）、意图卡片计数、
  `reduced-motion` 下过渡被压平的断言、全页截图。
- `scripts/verify/auth-pages-shot.mjs` 是仓库既有的同类脚本，提供了可参照的写法
  （Playwright + 多视口 + console/requestfailed 收集 + 版式断言）。

**缺的只有一件事：基线存储与比对。** 现有脚本只出图，不比对，不进门禁。

## 3. 精确范围

### 3.1 新增文件

| 文件 | 职责 |
| --- | --- |
| `scripts/verify/motion-baseline.mjs` | 采集 + 比对主脚本 |
| `scripts/verify/motion-baseline-targets.mjs` | 采集目标清单（页面、视口、主题、交互态） |
| `docs/artifacts/motion-baseline/**.png` | 基线图（需要纳入版本控制，见 §3.3） |
| `package.json` | 加两条 script：`verify:motion`（比对）与 `verify:motion:update`（更新基线） |

规模注意：主脚本容易膨胀。采集、比对、报告三件事职责不同，
超过 350 行就按这三段拆（`AGENTS.md` §5），不要靠注释分节硬塞在一个文件里。

### 3.2 采集目标

| 目标 | 理由 |
| --- | --- |
| `/playbook/foundations` | token 对照台。四档时长 + 三条曲线 + 三档弹性的静止态 |
| `/playbook/motion` | 17 条意图标本。**这是核心目标**，动效改动几乎都会反映到这里 |
| `/playbook/ui` | 47 个组件族的静止态，能抓到控件层改动的越界影响 |
| `/login` | 一个真实路由，验证 playbook 之外没被连带改坏 |

每个目标采集：亮 / 暗双态 × 桌面（1440×900）。
`/playbook/motion` 额外采一张 `reduced-motion: reduce`。

**动画中间帧不进基线。** 动效是时间函数，中间帧不可复现。基线只采**静止态**
（动画未触发 / 已结束），动效本身靠 §3.4 的计算样式断言保证。
这是刻意的取舍：截图比对负责"别的没坏"，计算样式断言负责"该对的对"。

### 3.3 基线图放哪

放 `docs/artifacts/motion-baseline/` 并纳入版本控制。

理由：`.data/` 已被 `.gitignore`（`AGENTS.md` §5 明令不提交），基线若不入库就无法跨会话、
跨机器比对，等于没有基线。代价是仓库体积增长——因此 §3.2 刻意把目标压到 4 个页面
而不是 46 个组件。若单张超过 ~400KB，先降到 1× `deviceScaleFactor` 再考虑扩范围。

### 3.4 计算样式断言（比截图更稳的那一半）

保留并扩充现有脚本已有的断言：

- 四档时长在浏览器里的计算值：`fast` → `0.15s`（校准后）、`base` → `0.22s`、
  `slow` → `0.36s`、`narrative` → `0.3s`；
- 三条曲线的 `transition-timing-function` 计算值与 `globals.css` 一致；
- `reduced-motion` 下 `.duration-base` 的计算值 ≤ 1ms
  （浏览器可能回报 `0.01ms` 或等价的 `1e-05s`，**按秒数值比较，不要字符串相等**——
  本轮已在这里踩过一次假失败）；
- `/playbook/motion` 意图卡片数等于 `MOTION_INTENT_COUNT`，且页面无「标本未登记」文案。

## 4. 执行步骤

1. 把 `.data/motion-playbook-shot.mjs` 的逻辑迁到 `scripts/verify/`，拆出目标清单模块。
2. 加基线比对：逐像素差异计数 + 阈值。阈值从严（建议差异像素占比 > 0.1% 即失败），
   宁可误报也不要漏报——03 批次要靠"零差异"这个强判据。
3. 加 `verify:motion:update`，且**必须显式调用才更新基线**。
   禁止在比对失败时自动覆盖基线，那会让设施失去意义。
4. 采集首版基线并提交。
5. 在 `00-README.md` §0.3 的共用清单里补一行 `pnpm verify:motion`。

## 5. 验证

- 首次采集后**立刻再跑一次比对**，必须零差异——这验证采集本身是可复现的
  （字体加载、动画未静止、时间戳水印都会让这一步失败，要在这里就修掉）；
- 故意改一处动效值（如临时把某控件改成 `duration-slow`），确认比对**能红**，
  然后还原。不做这个反向验证，就不知道设施是否真的在工作；
- 共用清单全套。

## 6. 风险与回滚

**风险**：Playwright 截图在不同机器 / 字体环境下可能不稳定，导致基线不可跨机器复用。
若首版就出现无法消除的抖动，退化方案是**只保留计算样式断言 + console 检查**，
放弃像素比对，并在本文档记录原因——**不要保留一个总是误报的比对**，
那比没有更糟（会训练执行者忽略它）。

**回滚**：纯新增设施，revert 即可，不影响任何产品代码。
